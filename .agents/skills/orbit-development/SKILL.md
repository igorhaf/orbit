# Orbit Development

Use the current Orbit implementation and authenticated `/architecture` API contract as the source of truth for boards and orchestration. Reject unknown mutation fields; do not invent card fields or recreate obsolete UI. Cards use one checklist and live context links. A card used as context is a parent; a card referencing it is a child. Checklist conversion keeps the originating card as parent. Structured hierarchy uses an explicit primary parent owned by the structured-view plugin: each card has zero or one parent and any number of children. Context associations remain many-to-many and never implicitly reparent a card. Checklist conversion assigns its origin as primary parent automatically. Resolve primary ancestors and their context associations dynamically for prompts; show inherited references separately from editable explicit associations. Moving a card changes only its primary parent, with cycle and same-board checks; Kanban and structured views display each card once. Convert checklist items through the native endpoint so parent and inherited contexts stay attached. Load project skills even when the card has no selected skills. Boards linked to an architecture reference may only use custom fields defined by that reference.

For work in an existing site, preserve its approved layout and components. Keep execution reports, prompts, internal research and validation evidence out of public pages. Validate real rendering and interactions before concluding a demand; a successful worker exit alone does not prove acceptance.

Cards have a basic layout independent of AI. Plugin cardLayouts contributions supply optional fields and slots; select them through /cards/:id/plugins, resolve declared dependencies, and preserve plugin data on removal. The software-development layout depends on the AI plugin. Only selected and enabled AI layouts show IA do cartão and prompt-runs in Execução. Live Contextos links remain core. Do not render the removed Execução opcional, Contexto, Limites de alteração or Integrações panels, even when a card has an execution configuration. File scopes and mandatory verification remain backend configuration. Validate both a configured demand and the Orbit reference card in the browser; API structure alone cannot prove interface consistency.

Primary card types are a separate plugin contribution from complementary card layouts. Root configures the instance catalog and may override availability per board; board settings inherit the global defaults unless explicitly overridden. When a board has zero or one effective type, hide card-type selection and derive the primary type from configuration. With multiple types, filter choices through RBAC permission `cards.type.<id>.use`. Never add type selection to project, board, or column creation; resolve card types from instance and board configuration. Keep type data and renderers in the contributing plugin, and allow other plugins to add complementary capabilities without changing the primary type.

Board visualizations are plugin contributions in `boardViews`. Quadro visual and Gestão estruturada use the same board/card records and require their own RBAC privileges (`views.board.use`, `views.structured.use`) in addition to board access, even when only one view exists. Hide the view selector when only one authorized renderer is available. Store view preferences and saved filters per user and board. Do not invent priority, sprint, status, or hierarchy fields: use existing lists, custom fields, assignees, dates, and context links. Open the existing card editor as a centered modal in both visual and structured views, preserving list position and filters, and apply live plugin availability to both the UI and direct API requests.

For supervised projects, configure `require_write_scope: true` in `.orbit/orbit.yaml` and give each demand an explicit `context.write_scope` of relative files through the execution configuration API. The executor checks the working tree, restores changes outside that list, and fails the run. This completion check supports project supervision; it does not replace operating system isolation or permission controls. Revalidate the actual files and browser results before updating checklists or accepting a run.

Configure `post_execution_checks` as arrays of executable and arguments, such as `[npm, run, check]`, for mandatory project validations. Both execution paths await these checks before reporting success; failure or timeout fails the run. These checks require `process.execute`. Keep validation scripts outside the allowed write scope of implementation demands. Text generation runs in read only mode and does not authorize source edits.

Keep the Orbit system responsive across mobile, tablet, and desktop viewports whenever implementing or changing user-facing features.

- Design layouts to adapt to narrow screens; avoid fixed widths and horizontal page overflow.
- Preserve usable navigation, forms, dialogs, tables, and primary actions on touch-sized screens.
- Check the affected flow at a narrow mobile width and a desktop width, and address any responsive regressions introduced by the change.
- Do not run Selenium inside Orbit or on this development host: the user withdrew authorization after a machine freeze. Do not automatically start another browser runner as a substitute. Validate with lint, TypeScript, unit tests and API reads sequentially; report browser validation as pending when it has not completed. Existing browser scripts are reference material and require a new explicit user authorization in a suitable environment before execution.
- Follow the repository's existing patterns and run relevant checks for the changed code.

Em projetos com escopo explícito e verificações obrigatórias, uma execução reprovada restaura também as alterações autorizadas da tentativa. Diretórios e caminhos por links simbólicos não são escopo de arquivos. As provas de navegador ficam privadas; testes não autorizam afrouxar os validadores.


Ao desenvolver plugins, primeiro procure capacidades compartilhadas e declare dependências reais em PluginDefinition.dependencies. Separe adaptadores de serviço de suas bases reutilizáveis (OAuth, cliente HTTP, executores), sem tornar obrigatória uma integração opcional. Desativar uma base suspende transitivamente dependentes, preserva seus estados desejados e seus dados; reativar não liga um dependente explicitamente desativado. Mostre estado efetivo, causa do bloqueio e dependentes afetados; publique mudanças autenticadas em tempo real. Valide também rotas, workers, webhooks e chamadas internas, além das actions do registry.

Para funcionalidades do Orbit e clientes derivados, como SAFDOULA, desenvolva no checkout compartilhado Orbit DEV, branch develop. O quadro Orbit é a referência arquitetural; os quadros dos clientes herdam o projeto Orbit (nativo). Separe capacidades reutilizáveis e configuração/dados institucionais em plugins e contextos adequados. Instâncias de clientes e PROD são destinos de publicação separados, sujeitos à autorização de deploy.
